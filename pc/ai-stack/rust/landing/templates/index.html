How I work

Nobody taught me any of this

Every system on this page I built by reading, trying it, breaking it and fixing it. No bootcamp, no team to fall back on, no one to hand it to when it got hard.

That is the part worth hiring. Certificates say I passed an exam. What I actually do is take a scope I have not seen before and keep going until it works — then write down what went wrong so the next person does not lose the same afternoon.

It changed how I learn, not how much: I go all the way into a problem and I do not come out until it is solved. Seventy-four rooms, a hundred and eighteen containers and a fault chased through three layers are all the same trait doing the same thing. Most employers treat it as a risk. It is the reason any of this exists.

None of this was knowledge I started with. I had not written PHP, I had not designed a schema, and I had never terminated TLS or read a reverse proxy config. I learned it the slow way, on a live system, with my own family using it.

And I use AI heavily — I would rather say so than have you wonder. It became available to me academically in my last semester, and it is how these pages get written as fast as they do. By hand I would have run out of gas long before this much existed. That is the honest trade: one person, a day job, and a system the family actually depends on.

What it does not do is the deciding or the finding. It is confidently wrong often enough that taking its word is how you ship a fault, and the failure I watch for hardest is code that only works because the tool made it work — a thing that passes because whatever wrote it also wrote what it was checked against. So I do not verify the tool with the tool. I research it out, read the forums, ask colleagues and friends what they make of an idea, and bring my own education and experience to it before I keep anything.

Prompting and pasting does not get you here. Somebody who had only done that would have no faults to write up, because they would never have found them. Every part of this site I have troubleshot myself, as deeply as I could. Five faults are written up in the engineering notes — the symptom, what it first looked like, and the cause two or three layers down — including the ones where I was wrong first.

The same problems, at home first

Why any of this transfers

A company does not need someone who has run containers. It needs someone who has had to decide who gets in, what happens when a certificate expires at 2am, and where the second copy lives. I have had to decide all of it, because there was nobody else to ask.

The numbers below were counted on the running systems, not estimated. They change; the shape does not.

Identity — one account, not thirty

30 hostnames · 117 access rules · one sign-in

Every private service sits behind a single OIDC issuer I run: Immich, Jellyfin, Kavita, Audiobookshelf, two wikis, the recipe library and two phone apps I wrote. One account per person, one place to revoke it, and no service holding its own password list.

Access — two ports for the whole estate

80 and 443 · 34 certificates · renewed unattended

Nothing is published on a port of its own. A reverse proxy terminates TLS for every hostname, renews all 34 certificates without being asked, and forwards to services that are not reachable from outside at all. Remote shell rides on 443 alongside the web traffic, so port 22 is closed to the internet.

Language models, run in-house

Local weights · one gateway · nothing leaves the house

The assistants across these sites answer from models running on my own hardware, reached through a single gateway that holds the credentials and routes by task, so an application never holds a key and the model behind it can be swapped without touching the application. Speech synthesis runs on the low-power machine; the GPU is reserved for what needs it.

Change control and recovery

Self-hosted Git · 118 containers · declared, not clicked

Source lives in a Git service I host, and the machines are described in compose files rather than assembled by hand — so a rebuild is a file, not a memory. When something is patched into a running container it is written back into the build context in the same sitting, because code that exists only in a running container is not deployed, it is borrowed, and the bill arrives at the next rebuild.
